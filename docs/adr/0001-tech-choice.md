# 0001: Go ゼロ依存（stdlib + go:embed + 素の JS/HTML）で作る

- Status: accepted
- Date: 2026-07-19

## Context

beadmap はローカル開発補助ツールであり、beads のデータを読むだけの進捗ビューア。
開発補助ツールにフレームワークを持ち込むと、依存更新・ビルド・脆弱性対応が
ツール自体の保守コストになる。また「導入 1 コマンド・起動 1 コマンド」の
体験が薄れると、俯瞰したい時にサッと開く道具として使われなくなる。

比較した候補:

| 候補 | 利点 | 見送り理由 |
| --- | --- | --- |
| Next.js | 連載のデモ本体と同スタック | ビューア 1 画面に対して依存・ビルドが過剰。node_modules の保守がツールの保守になる |
| Node/TS + Express 等 | 書き慣れている | 依存ゼロにはならず、実行に Node ランタイムと install が要る |
| **Go stdlib のみ** | 外部依存ゼロ・単一バイナリ・`go install` 一発・クロスプラットフォーム | Go はこの連載文脈で初採用（学習コスト） |

## Decision

- Go 標準ライブラリのみで実装する（net/http + go:embed + encoding/json）。外部依存ゼロ
- UI はビルドなしの素の HTML/CSS/JS を go:embed で単一バイナリに同梱する
- `go install github.com/syotakokichi/beadmap@latest` で導入、`beadmap` 1 コマンドで
  起動（127.0.0.1・ポート自動回避・ブラウザ自動オープン）
- 層を collector（データ収集）/ server（配信）/ ui(表示) に分け、各層に単体テストを置く

## Consequences

- 依存更新・ビルド事情から解放され、保守はほぼゼロになる
- 明示的で冗長な Go のコードは、AI に書かせた成果物を人間が検証しやすい
  （何が起きるかがコードに全部書いてある）
- フレームワークの UI 部品は使えないため、ツリー表示等は素の JS で自作する
- デモ本体（Next.js）とスタックが分かれる。「用途で技術を使い分ける」判断として
  連載でもそのまま扱う
- Go 初採用の学習コストは、規模を小さく保つこと（3 層・1 画面）で抑える
