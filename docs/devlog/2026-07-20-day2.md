## 境界ゲートが実戦で仕事をした

Day 1 で「コードより先に」置いた境界ゲートが、公開直前に本当に機能した。

- 禁止語リストに **個人メールアドレス** を追加したところ、ゲートが NG を返した。
  ヒット箇所は `.beads/issues.jsonl` の owner フィールド全件と、git の全コミット
  author/committer。ツールのデフォルト（bd は git config から owner を拾う）と
  git のグローバル設定が、意識しないまま公開物に個人情報を運び込む経路だった
- **未公開のうちに検出できた**のがすべて。対応は退避 + 再構築ルートで行った:
  1. repo ローカルの git identity を GitHub noreply アドレスに変更
  2. `.beads` を退避して bd init し直し、クリーンな jsonl から全 issue を再 import
     （ID・状態・依存関係・タイムスタンプはすべて保全。ready / blocked の算出も正常）
  3. `git filter-branch` で全コミットの author/committer を noreply 化し、
     旧 jsonl blob 内のアドレスも置換。refs / reflog / gc を掃除
- 検証: 履歴内のヒット 0 件・boundary-check PASS（履歴検査込み）・`go test` green

学び: 境界ゲートは「語を足すと過去の全履歴も検査し直される」設計にしておくと、
後から気づいた漏洩語をリストに足すだけで遡って検出できる。fail-closed
（リストが読めなければ失敗）と合わせて、ゲートを「通れば安全」の一点に寄せられる。

## 公開直前の方針すり合わせ — 「誰に何を見てもらうか」

公開作業に入る前に、目的のズレを 1 つ見つけて直した。

- オーナーの意図は「[settlebase](https://github.com/syotakokichi/settlebase) のタスクを
  全体進捗を俯瞰しながら進めている様子を、外の人に実際に見てもらう」こと。
  ところが計画では、外の人が画面を見られる経路が記事のスクリーンショットしかなかった
- 結論: **静的デモページを主経路に格上げ**する。GitHub Pages に置き、
  beadmap 自身（bm-\*）と settlebase の実データ（既公開 jsonl のスナップショット）を
  切替表示する。サーバなし・ブラウザ内描画のみなので read-only 契約は不変
- 公開と告知は分離する: repo はこの日に公開し、X 告知・記事はデモが揃ってから
- 「リポジトリを settlebase と分けたのは正しかったか」も検証した。結論は分離維持。
  settlebase のデータは公開済みなので独立 repo のデモからでも映せるし、
  同居させると「settlebase 専用ツール」に見えて汎用ビューアの筋と
  `go install` の導入しやすさが失われる
