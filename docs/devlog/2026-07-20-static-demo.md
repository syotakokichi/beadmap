# devlog: 静的デモ — settlebase の進捗俯瞰を、ブラウザだけで見てもらう

日付: 2026-07-20

## 目的のすり合わせから始まった

v1 公開の直前に見つけた目的のズレ（[Day 2](2026-07-20-day2.md) 参照）の答えがこのデモ。
「[settlebase](https://github.com/syotakokichi/settlebase) のタスクを、全体進捗を
俯瞰しながら進めている様子」を外の人が**実際に画面で見られる**入口を作る。

作る前に方針 4 点を赤ペン確認（1 往復・全て推奨案で採用）:

1. **配信方式** — GitHub Actions workflow で `ui/` を単一ソースのまま組み立てる
   （repo 内に UI の複製を持たない。ドリフトしない）
2. **URL** — Pages のルートに直接デモ（開いたら即デモ）
3. **初期表示** — settlebase（連載の主役）
4. **静的の明示** — ヘッダー下の常時バナー + スナップショット取得日

## 仕組み

- `demo/demo-config.js` が `window.BEADMAP_DEMO` を定義していれば、UI は API の代わりに
  同梱スナップショット JSON を読む（`dataSource` の差し替え 1 箇所）。
  この設定はデプロイ時にのみ `index.html` へ注入され、ローカル起動のライブ UI には入らない
- データは `go run ./cmd/gendemo` で生成（collector をそのまま流用し、
  `/api/snapshot`・`/api/closed` と同じ形の JSON をファイルに書く）。
  ローカルの絶対パスは公開 JSON に含めない
- サーバなし・ブラウザ内描画のみ。Go バイナリ側の read-only 契約（127.0.0.1・GET のみ・
  固定引数）には一切触れていない
- 静的スナップショットであることはバナーと取得日で常時明示（staleness 思想の踏襲）

## 小さな設計判断

- **空ビューへのフォールバック**: settlebase は現時点で全タスクが closed
  （立ち上げ期の 9 件）。初期ビュー「進行中」だと第一印象が「該当なし」になるため、
  デモモードだけ「件数のあるビューを初期選択する」ようにした。データを盛らず、
  見せ方だけ直す（連載が進めば settlebase 側の open が増え、自然に画が変わる）
- **自動更新はしない**: デモは静的スナップショットなので 30 秒ポーリングを止めた。
  データの自動更新（Actions で定期取得）はスコープ外とし、必要になったら別タスクで判断
  → 同日追記で実装した（下記）

## 検証

- Pages と同じ手順でローカルに組み立て、ブラウザで確認: 初期表示 settlebase →
  closed 9 件へ自動フォールバック / beadmap への切替で「進行中: bm-ftm（このデモ自身の
  タスク）」が映る自己言及 / 詳細ペイン・フィルタ・opt-in 取得も静的データで動作
- `go vet` / `go test` / markdownlint / lychee / 境界ゲート通過後に公開

## 自動更新と「これから作るもの」（同日追記）

公開後にオーナーと方向を確認し、2 点を足した。

- **デモデータの毎日自動更新**（update-demo-data.yml）。設計はローカルの公開フローと同じ
  「安全ゲートを通ったものだけを出す」構造の自動化:
  1. 入力は公開リポジトリの公開 jsonl のみ（新しい露出がない）
  2. 境界ゲートは fail-closed のまま CI 化 — 語リストは Actions secret に置き、
     未設定・空なら更新を中止。ログには語の内容もヒット詳細も出さない
  3. ゲート通過後、**データに実変化がある時だけ** commit / push（タイムスタンプ行だけの
     変化は無視）。だから画面の取得日は「最後にデータが動いた日」を正直に指す
- **settlebase にロードマップを公開起票**。これまで settlebase の beads は立ち上げ期の
  closed 9 件だけだったが、この先の道（UI 縦切り・ロール管理・バックエンド構成の比較・
  振替・maker-checker 承認・append-only 台帳・監査ログ）を依存関係付きで起票した。
  デモには「終わったもの」だけでなく「着手可能 3・ブロック中 4」が映り、
  何をどの順で作ろうとしているかの全体像が見える

## 事後レビューの反映（同日追記）

告知前の最後のゲートとして、独立 3 レビュアー（fact/risk・構成整合・計画照合）で
事後検証した。自動更新のような「無人で公開物を更新する仕組み」は、
人の目が挟まらないぶんゲート自体の穴が直撃する — 実際に効いた指摘が出た:

- **公開 HEAD と異なるデータを同梱していた**: 依存関係の追加が jsonl の auto-export
  より先に staging されて公開 push から漏れ、初回同梱データ（依存 4 本）と公開 HEAD
  （依存 1 本）が食い違っていた。自動更新が公開 HEAD から再生成した時点で
  デモの表示が変わってしまった。→ settlebase 側の export を commit / push し直し、
  gendemo が生成元の commit SHA（未コミット変更があれば +dirty）を JSON に記録する
  ようにして、この食い違いを検知可能にした
- **fail-closed の穴**: 語リストがコメント行だけだと「検査語 0 語」で通過し得た。
  grep / git の実行エラーも「ヒットなし」と同一視していた。→ 有効語 0 語は失敗、
  実行エラー（exit 2 以上）はヒットなしと区別して失敗、CRLF も正規化
- **履歴検査の浅さ**: CI の shallow clone では全履歴を検査できない（fetch-depth: 0 を
  必須化）。blob 検査だけでは author / committer / コミットメッセージを見ない
  （メタデータ検査を追加）
- **ルールと実装の矛盾**: 「境界チェックは CI に含めない」という公開ルールの明文が
  secret 方式の新 workflow と正面衝突していた → 「原則ローカル・例外は自動更新のみ」
  に運用ルールを更新
- ほか: デプロイ失敗の可視化（pages.yml を workflow_call で直接呼ぶ）、main 固定、
  バナー文言「自動更新なし」の矛盾解消、取得日表示のタイムゾーン修正
