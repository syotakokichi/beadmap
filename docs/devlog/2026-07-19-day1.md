# devlog: Day 1 — repo 立ち上げ・名前選定・境界ゲート

日付: 2026-07-19

## 何を作るか

beads（bd CLI）のタスクデータを **読むだけ** のローカル進捗ビューア。
CLI は個々のタスク操作には強いが、プロジェクト全体の進捗・依存関係・停滞の俯瞰が弱い。
そこを「正本には一切書き込まない読み取り用の地図」で補う。

位置づけを最初に固定した:

- **beads が正本**（正確には正本は Dolt DB。`.beads/issues.jsonl` はビューア・相互運用向けの export）
- **beadmap は地図**。閲覧専用に徹し、作成・更新・close の API をそもそも持たない
- read-only は「気をつける」ではなく構造で保証する（127.0.0.1 バインド・GET 以外 405・
  bd 実行は読み取り専用固定引数のみ・外部サービスへの自動アクセスなし）

## 名前選定（best-of-n）

repo 名は 1 案に決め打ちせず、軸を分けた 4 案を作って人間がブラウザ arena で採用する方式にした。

| 案 | 軸 |
|----|-----|
| bdboard | 直球・機能名（bd + board） |
| **beadmap** | 位置づけメタファー（正本の読み取り用地図） |
| beadscope | 俯瞰・観察器具 |
| juzu | 和メタファー（数珠つなぎ＝依存関係） |

採用は **beadmap**。採用理由は「ロードマップみたいな印象に近くて良い」。
設計思想（読み取り用の地図）と名前が一致していて、記事でも「地図は現地を書き換えない」の
比喩で read-only 契約を説明できる。

候補出しの段階で GitHub の名前衝突も確認した。soroban（そろばん＝珠の俯瞰、と思ったら
Stellar のスマートコントラクト基盤と大衝突）と bdv（rootkit と検索が被る）はこの時点で落とした。

## 境界ゲートを最初に置く

この repo は本業で得た知見の「一般化パターン」だけを持ち込む再実装であり、
本業のコード・画面・固有情報は一切含めない。それを担保する仕組みを **コードより先に** 整備した:

- `scripts/boundary-check.sh` — 非公開の語リスト（repo 外 `~/.config/beadmap/boundary-words.txt`）に
  載る語が repo 内に 1 件でもあれば失敗。リストが読めない場合も失敗する（fail-closed）
- 公開は全実装完了後の境界ゲート通過後に一発で行う。それまで push しない

## 今日の判断
