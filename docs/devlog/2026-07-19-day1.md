# devlog: Day 1 — repo 立ち上げ・名前選定・境界ゲート

日付: 2026-07-19

## 何を作るか

beads（bd CLI）のタスクデータを **読むだけ** のローカル進捗ビューア。
CLI は個々のタスク操作には強いが、プロジェクト全体の進捗・依存関係・停滞の俯瞰が弱い。
そこを「正本には一切書き込まない読み取り用の地図」で補う。

位置づけを最初に固定した:

- **beads が正本**（正確には正本は Dolt DB。`.beads/issues.jsonl` はビューア・相互運用向けの export）
- **beadmap は地図**。閲覧専用に徹し、作成・更新・close の API をそもそも持たない
- read-only は「気をつける」ではなく構造で保証する（127.0.0.1 バインド・GET 以外 405・
  bd 実行は読み取り専用固定引数のみ・外部サービスへの自動アクセスなし）

## 名前選定（best-of-n）

repo 名は 1 案に決め打ちせず、軸を分けた 4 案を作って人間がブラウザ arena で採用する方式にした。

| 案 | 軸 |
| --- | --- |
| bdboard | 直球・機能名（bd + board） |
| **beadmap** | 位置づけメタファー（正本の読み取り用地図） |
| beadscope | 俯瞰・観察器具 |
| juzu | 和メタファー（数珠つなぎ＝依存関係） |

採用は **beadmap**。採用理由は「ロードマップみたいな印象に近くて良い」。
設計思想（読み取り用の地図）と名前が一致していて、記事でも「地図は現地を書き換えない」の
比喩で read-only 契約を説明できる。

候補出しの段階で GitHub の名前衝突も確認した。soroban（そろばん＝珠の俯瞰、と思ったら
Stellar のスマートコントラクト基盤と大衝突）と bdv（rootkit と検索が被る）はこの時点で落とした。

## 境界ゲートを最初に置く

この repo は本業で得た知見の「一般化パターン」だけを持ち込む再実装であり、
本業のコード・画面・固有情報は一切含めない。それを担保する仕組みを **コードより先に** 整備した:

- `scripts/boundary-check.sh` — 非公開の語リスト（repo 外 `~/.config/beadmap/boundary-words.txt`）に
  載る語が repo 内に 1 件でもあれば失敗。リストが読めない場合も失敗する（fail-closed）
- 公開は全実装完了後の境界ゲート通過後に一発で行う。それまで push しない

## 今日の判断

- 技術は Go ゼロ依存（stdlib net/http + go:embed + 素の JS/HTML）。選定比較は ADR-0001 に記録
- スコープ・画面構成は「サマリータイル / 一覧・親子ツリー / 停滞順 / 詳細ペイン一段 / closed opt-in」。
  実装前に画面レイアウトを赤ペン確認してから作る

## ハーネス骨子の赤入れ反映（同日）

CLAUDE.md 骨子と `.claude/` 配置は、書き始める前に赤ペン確認（1 往復）で確定した。採用と理由:

- **repo 自身に bd init（prefix `bm`）して自己言及運用にする** — 自分のダッシュボードに
  自分のタスクが映る構造がそのまま連載の柱になり、公開 repo での実運用一巡もこの repo で完結する
- **CLAUDE.md は既存デモ repo（settlebase）の型を踏襲し、read-only 契約の節を追加** —
  連載デモ repo 間で型が揃う
- **README は日本語** — 連載読者と揃える
- 確認された前提: 公開するのは repo（コード）と境界チェック済みスクリーンショットのみ。
  動作する UI は 127.0.0.1 専用のローカルツールで、ホスティングはしない

## 自己言及運用の開始

- v1 リリースを epic に、collector / server / ui / docs / 公開ゲートの 5 タスクを起票。
  実装済みの collector・server は close、ui を claim、公開ゲートは ui・docs が閉じるまで blocked
- これで open / in_progress / blocked / closed / epic の全状態が自分の実データで揃い、
  そのまま UI 実装の確認データになる
- 気づき①: `--deps blocks:` は「新しい issue が指定先をブロックする」向きで、意図
  （新しい issue が指定先を待つ）と逆だった。`bd dep add <待つ側> <待たれる側>` で修正
- 気づき②: issues.jsonl の自動 export には 60 秒の throttle があり、bd の書き込み直後は
  jsonl が古いことがある。staleness 表示（ファイル更新時刻の常時表示）の必要性を
  自分のデータで最初に踏んだ

## 方向修正: 「ローカル専用」を売りにしない（同日）

上の節で「動作する UI はホスティングしない」と書いたが、方針を一部修正した。

- 伝えたいことの主役は「**タスク管理は UI で俯瞰するとこう見やすい**」であって、
  ローカル専用であること自体ではない。README のピッチを俯瞰の見やすさ中心に直した
- read-only（書き込み API を持たない）だからこそ、サンプルデータ同梱の
  **静的デモページ**（ブラウザ内描画のみ・サーバなし・bd なし）を安全に出せる。
  install 不要で気軽に触ってもらう入口として v1 公開後に作る（bead 起票済み・UI 完成待ち）
- Go バイナリ側の契約（127.0.0.1 バインド・GET のみ・固定引数）は変えない。
  これは売り文句ではなく安全性の担保として残る

## UI 実装（同日）

画面レイアウトは実装前に赤ペン確認（1 往復）で確定した。採用: 日本語ラベル /
詳細ペインは右サイド / ダークテーマ（いずれもモック案どおり）。

- 素の HTML/CSS/JS 3 ファイル（ビルドなし・go:embed 同梱）。データ取得は
  `dataSource` 1 箇所に集約し、静的デモ（同梱 JSON 差し替え）に備えた
- 実データで表示確認: 自 repo（7 件・全ステータス）、別 repo その1（9 件・全 closed）、
  別 repo その2（67 件）。いずれも「一覧 + closed の合計 = jsonl 全件」「ready / blocked 件数が
  bd ライブクエリと一致」を確認。epic ツリー展開・詳細ペインの一段表示・closed opt-in・
  検索 / priority フィルタ・停滞バッジも動作
- 副産物: 別オリジンのページから API を fetch すると CORS で弾かれることを確認
  （CORS ヘッダを一切出していないため）。read-only 姿勢として好都合なのでこのままとする

## UI 改善ラウンド（同日・人間レビューの反映）

実物を触ってもらったフィードバックを反映した。

- **詳細ペインを広く**: 既定の幅バランスを一覧 40% / 詳細 60% に変更。
  bead の中身（description / design）を読む時間の方が長い、という実感に合わせた
- **ペイン幅のドラッグ調整**: 一覧と詳細の間にスプリッタを置き、幅を localStorage に保存
- **Markdown レンダリング**: description / design / notes を素の pre 表示から
  自前レンダラーでの整形表示に変更（見出し・リスト・チェックボックス・表・
  コードフェンス・引用・太字・リンク対応、約 120 行）。ゼロ依存の制約下なので
  ライブラリは使わず、全テキストをエスケープしてから自前タグへ変換する方式で XSS を防ぐ
- **書く側も整える**: bead の description / design 自体を箇条書き・番号・表で
  構造化して書く運用に変更（読み手がいる前提のタスク記述は、CLI で見ても UI で見ても効く）
